---
title: Small Tools Beat Big Plans
description: Why I stopped designing platforms and started shipping utilities that solve exactly one problem.

Every large project I have abandoned started the same way: a document describing
a system, not a problem. The document was always correct and always useless. It
described what the thing would be once it existed, and said nothing about the
first week of it existing, which is the only week that decides anything.

The utilities I still use years later were all written in an afternoon to fix
something that had annoyed me three times in a row. The annoyance was the spec.
There was no roadmap because there was no second feature, and there was no
second feature because the first one had already finished the job.

This is not an argument against ambition. It is an argument about sequencing. A
platform is what a tool becomes after enough people ask for the same next step.
It is a poor thing to start with, because starting with it means guessing which
step they would have asked for.

The practical rule I follow now is that the first version must be useful to one
person on the day it is written. If it is not, I have designed a plan instead of
a tool, and I should put the document away and go fix the annoyance.
